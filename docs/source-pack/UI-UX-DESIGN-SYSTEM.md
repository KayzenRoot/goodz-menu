# Goodz Menu — UI/UX Design System

Status: `BASELINE_V0.1 / REVIEW_PENDING`  
Authority domain: `UX + REQUIREMENT`

## 1. Product experience objective

Goodz Menu must feel like a purpose-built operating system for food businesses, not a generic admin template with a logo swap.

The interface must combine:
- operational speed;
- visual confidence;
- strong information hierarchy;
- premium finish;
- high legibility;
- predictable interaction;
- responsive behavior;
- accessible controls;
- restrained but expressive motion.

The design may be visually rich, but business speed and comprehension outrank decoration.

## 2. Experience families

Goodz has four primary first-party experience families:

### 2.1 Operations Shell
Used by POS, cash, orders, inventory and high-frequency staff workflows.

Priority:
1. speed;
2. touch/keyboard efficiency;
3. status clarity;
4. error prevention;
5. resilience.

### 2.2 Owner Shell
Used by dashboards, finance, AI, reports, treasury and management.

Priority:
1. comprehension;
2. prioritization;
3. explainability;
4. decision support;
5. dense but readable information.

### 2.3 Storefront Shell
Used by end customers ordering through Goodz Online.

Priority:
1. appetite/visual merchandising;
2. conversion;
3. clarity;
4. fast mobile checkout;
5. brand differentiation.

### 2.4 Platform Admin Shell
Used by Goodz platform operators.

Priority:
1. risk awareness;
2. global search/filter;
3. high-density operational views;
4. tenant/user/billing/system context;
5. stronger confirmation for privileged actions.

These shells share tokens/components where appropriate but are not forced into one identical layout.

## 3. Visual character

The baseline visual language is:

> **Warm precision + layered glass + operational clarity.**

Characteristics:
- crisp typography;
- controlled translucency;
- layered surfaces;
- soft depth;
- strong state colors;
- restrained glow/accent;
- rich food imagery where appropriate;
- compact operational surfaces where speed matters.

Glass is a hierarchy tool, not a wallpaper effect.

## 4. Theme system

Every first-party application shell supports:
- Light;
- Dark;
- System.

Theme selection is a user preference unless a higher policy locks it for a special surface.

Both themes must be designed independently enough to preserve contrast and hierarchy. Dark mode is not generated by simply inverting colors.

## 6. Brand accent strategy

Tenant storefront branding may alter approved brand tokens without changing semantic state colors.

An establishment may customize:
- primary brand;
- secondary brand;
- accent;
- background family;
- heading/body font from approved catalog;
- radii/density/layout preset;
- hero/card treatment.

It may not redefine:
- danger as green;
- success as red;
- focus visibility into invisibility;
- mandatory accessibility/contrast constraints.

## 7. Typography

Typography system must define:
- display;
- page title;
- section title;
- card title;
- body;
- compact body;
- label;
- helper;
- caption;
- numeric/KPI;
- monospace/code/error ID where needed.

Financial/numeric values must use a treatment that improves scanning and alignment.

Storefront display type may be more expressive than operations/admin UI.

## 8. Spacing and density

Use a finite spacing scale.

Supported density modes:
- comfortable;
- compact;
- touch-optimized where appropriate.

POS defaults to touch-efficient spacing.

Data-heavy admin/finance can support compact density without shrinking touch targets below accessibility minimums.

## 9. Radius, border and elevation

Tokens:
- radius-xs/sm/md/lg/xl/pill;
- border-subtle/standard/strong;
- shadow-1..n;
- glass-blur-1..n;
- elevation-0..n.

Rules:
- higher elevation means stronger importance/temporary overlay;
- not every card is elevated;
- nested cards should avoid “card inside card inside card” visual noise;
- destructive dialogs can use stronger contrast rather than excessive shadow.

## 10. Goodz Glass System

Glassmorphism is allowed for:
- navigation shells;
- floating toolbars;
- overlays;
- drawers;
- command palette;
- selected premium dashboard modules;
- storefront hero/chrome;
- contextual actions.

Avoid strong glass in:
- dense tables;
- long text;
- critical forms;
- high-frequency POS product grids when blur harms performance;
- accessibility-sensitive contrast zones.

Glass tokens must control:
- opacity;
- blur;
- border;
- backdrop tint;
- shadow;
- optional glow.

Reduced-transparency mode should be possible if required by accessibility/performance.

## 11. Layout system

Desktop shells:
- optional collapsible sidebar;
- top command/header bar;
- contextual secondary navigation;
- responsive content grid;
- optional right insight panel.

Mobile:
- prioritize one primary task;
- bottom navigation or compact app navigation where appropriate;
- avoid desktop tables squeezed into small screens;
- use cards/list/detail or horizontally scrollable data only when justified.

## 12. Navigation

Navigation must support:
- persistent module identity;
- breadcrumbs for deep hierarchy;
- global search/command palette;
- recently used/favorites where useful;
- explicit tenant/branch switcher;
- visible environment/platform-admin context to avoid dangerous mistakes.

## 13. Goodz Command Palette

Keyboard-triggered universal action/search surface.

Potential actions:
- search product/customer/order;
- navigate module;
- create sale/payable/purchase;
- open report;
- ask Goodz AI;
- switch branch;
- open settings.

Command results must respect permissions and tenant scope.

## 16. Goodz Feedback System

Feedback types:
- SUCCESS
- CONFIRMATION
- INFORMATION
- WARNING
- ERROR

- UNDO

Feedback presentation depends on consequence.

- modal/confirm dialog for action requiring explicit choice;
- notification center for durable asynchronous event.

## 17. Toast design

A Goodz toast contains:
- semantic icon/animation;
- concise title;
- optional detail;
- optional action;
- optional safe error/correlation code;
- progress indicator when useful.

Rules:
- visible but non-blocking;
- keyboard accessible;
- screen-reader announced with appropriate urgency;
- no secret/stack trace;
- stack/deduplicate intelligently;
- critical errors persist or promote to durable notification when necessary.

### Success
Short, confident confirmation.

Example:
`Pedido #1042 confirmado`

### Error
Explain what failed, what remains safe, and what the user can do.

Example:
`Pagamento não concluído. O pedido continua salvo. Código GM-PAY-2048.`

### Offline
State explicitly that operation is local/pending and what will happen on reconnect.

## 18. Confirmation animation

Material successful actions may use brief celebratory confirmation:
- check morph;
- subtle pulse;
- success surface;
- micro-confetti only for rare delight moments, not repetitive POS transactions.

Routine operations should remain fast and quiet.

## 19. Error Experience

User-facing errors have:
1. human explanation;
2. impact;
3. next action;
4. safe error code;
5. retry when safe.

Technical diagnostics have:
- correlation ID;
- route/module;
- tenant-safe context;
- stack/logs in observability only.

Never reveal:
- SQL;
- environment values;
- credentials;
- token contents;
- internal stack traces.

## 20. Loading system

Prefer:
- optimistic UI for safe reversible local interactions;
- skeleton for predictable content;
- progress for measurable long jobs;
- spinner only for brief indeterminate tasks.

Avoid blank screens.

For long jobs:
- allow navigation away;
- persist job state;
- notify on completion.

## 21. Empty states

Empty state should answer:
- what this area is;
- why it is empty;
- what the user can do next.

Do not use generic “No data” when a more useful explanation is possible.

## 22. Goodz Motion System

Motion token groups:
- instant;
- fast;
- standard;
- deliberate;
- expressive.

Motion categories:
- microinteraction;
- state transition;
- navigation;
- overlay;
- confirmation;
- loading;
- data update;
- spatial reordering.

Rules:
- use transform/opacity-friendly animation where practical;
- avoid long blocking motion;
- no animation delays on critical POS actions;
- repeated high-frequency actions use minimal motion;
- expressive motion is reserved for meaningful context change.

## 23. Reduced motion

Respect OS/browser reduced-motion preference.

When reduced:
- remove parallax;
- remove large spatial travel;
- simplify spring/bounce;
- preserve state visibility via fade/instant transitions.

Functionality cannot depend on motion.

## 28. Settings inheritance UX

Example:
```text
Theme
User: Light       ← effective
Tenant default: Dark
Platform default: System
```

Locked policy:
```text
MFA for Platform Admin
Enabled
Locked by Platform Security Policy
```

Do not make users guess why a control is unavailable.

## 33. Storefront product imagery

Image handling prioritizes:
- sharp food presentation;
- stable aspect ratios;
- responsive sources;
- fast initial view;
- lazy-load below fold;
- placeholder/skeleton;
- meaningful alt text.

Image quality must not destroy storefront performance.

## 34. Storefront conversion UX

Principles:
- categories easy to reach;
- price visible;
- modifiers understandable;
- cart accessible;
- checkout progress clear;
- fees/minimum/delivery estimate shown before final confirmation when possible;
- validation errors local and recoverable.

## 35. Super Admin shell

Distinct visual context from tenant admin.

Must make global authority obvious:
- Platform Admin badge/header treatment;
- current tenant context if drilling into tenant;
- privileged action confirmation;
- environment indicator;
- audit link.

High-risk actions use:
- explicit target;
- impact summary;
- reason;
- reauthentication/MFA when required by Security;
- reversible/irreversible label.

## 36. Tables and data grids

Data grids support:
- sortable columns where useful;
- filters;
- saved views later;
- sticky key columns selectively;
- row actions;
- bulk actions with explicit selection;
- loading/error/empty states;
- responsive alternate representation.

Money/status cells use consistent semantic alignment.

## 37. Charts

Charts must:
- answer a question;
- include units/timeframe;
- support tooltip/legend;
- avoid unnecessary 3D;
- avoid color-only differentiation;
- display no-data and partial-data states.

AI-generated commentary must not visually obscure raw metrics.

## 38. Forms

Rules:
- label always visible for business-critical fields;
- placeholder is not a label;
- helper text for domain-specific meaning;
- errors near field;
- preserve user input on recoverable error;
- dangerous changes show impact before save.

Long configuration forms should use sections or progressive disclosure.

## 39. Keyboard and focus

Desktop operational/admin surfaces must support:
- logical tab order;
- visible focus;
- escape-close for overlays when safe;
- enter/space semantics;
- documented POS shortcuts;
- command palette shortcut.

No keyboard trap.

## 40. Touch targets

High-frequency controls must be touch-friendly.

POS and mobile ordering prioritize generous targets and spacing.

Compact desktop density does not justify unusably small interactive hit areas.

## 41. Accessibility baseline

Target baseline to be frozen numerically in Test/Benchmark Plan, with intent toward current WCAG AA-level conformance for applicable flows.

Mandatory:
- semantic structure;
- keyboard access;
- focus visibility;
- label relationships;
- status announcements;
- color contrast;
- non-color state cues;
- reduced motion;
- alt text/media semantics;
- accessible modal focus management.

## 42. Responsive strategy

Breakpoints are implementation details, but behavior is contractual:
- no clipped critical action;
- no horizontal viewport overflow for primary workflows;
- desktop grids convert sensibly;
- dialogs become drawers/full-screen where appropriate;
- charts remain readable;
- POS prioritizes its task.

## 43. Performance UX

Visual richness must obey:
- blur/effects budget;
- animation budget;
- image budget;
- chart complexity budget.

No decorative effect may materially delay:
- add-to-cart;
- checkout;
- payment;
- order confirmation;
- critical admin action.

Exact budgets belong to Test/Benchmark Plan.

## 44. Progressive disclosure

Advanced options should not overwhelm new users.

Use:
- simple default flow;
- expandable advanced settings;
- expert mode where justified.

Never hide critical cost/fee/security information behind obscure affordances.

## 45. Permission UX

When action unavailable:
- distinguish no permission from system error;
- explain required role/process where safe;
- do not show controls that tempt unauthorized action unless discoverability benefits justify disabled state.

## 46. Offline UX

Persistent but unobtrusive state:
- Online
- Offline
- Syncing
- Pending
- Conflict/attention

Offline sale must show:
- whether local operation is accepted;
- what awaits sync;
- when user action is needed.

## 47. Destructive actions

Use graduated confirmation.

Low-risk reversible:
- undo toast may suffice.

High-risk:
- confirm dialog.

Very high-risk:
- explicit target/impact;
- reason;
- strong authentication if Security requires;
- type-to-confirm only when evidence shows value, not as theater.

## 48. Visual validation

A feature is not UI-DONE until applicable states are visually reviewed:
- Light;
- Dark;
- desktop;
- mobile;
- loading;
- empty;
- error;
- success;
- permission denied;
- offline/sync when applicable.

Critical components require screenshot/visual-regression coverage once implementation begins.

## 49. Storefront personalization guardrails

Allowed:
- approved theme tokens;
- approved fonts;
- layout presets;
- component variants;
- banners/content;
- imagery;
- density/radii.

Disallowed by default:
- arbitrary JS;
- unrestricted CSS;
- hiding legal/fee/checkout requirements;
- inaccessible semantic-color override.

## 50. Goodz visual acceptance principles

A UI should be rejected when:
- it looks generic/unbranded;
- information hierarchy is unclear;
- dark mode is an afterthought;
- glass harms text/readability;
- animation slows operation;
- loading/error/empty states are missing;
- mobile is simply shrunk desktop;
- tenant/user settings inheritance is confusing;
- privileged context is ambiguous;
- AI recommendations do not distinguish fact from inference.

## 51. Implementation freedom

This baseline does not freeze:
- exact component library;
- exact CSS framework;
- exact font family;
- exact hex values;
- exact animation library;
- exact breakpoint values.

Those choices must satisfy this contract and be validated at implementation time.
